1. Learning objectives

After studying this page and walking the live app, a new systems engineer should be able to:

  • Translate a contract operational need into stakeholder and system requirements.
  • Separate what the system must do (requirements) from how it is built (design).
  • Write testable acceptance criteria (Given / When / Then or measurable shall statements).
  • Model dynamic behavior with state machines and sequence diagrams.
  • Trace a requirement → design element → verification method.
  • Identify external interfaces (users, TEMPO, email, Excel contract package).
Teaching note: Artifacts below are reverse-engineered from the running implementation (app/ services, models, routes). In a greenfield program you would produce many of these before coding.

2. Operational need & system context

Need: SDC staff supporting the FOSC must record attendance that is auditable, matches FOSC schedule rules (9/9/9/9/4 week, paid lunch, BEOD), supports leave, and can be exported in the Lockheed weekly/quarterly time-record format with TEMPO discrepancy analysis.

flowchart LR Emp[Employee] Mgr[Manager / Supervisor] STT[SDC Time Tracker] TEMPO[Lockheed TEMPO] SMTP[Email SMTP] FOSC[FOSC Excel package] Emp -->|PIN punches leave| STT Mgr -->|Approve import export| STT STT -->|Import weekly hours| TEMPO STT -->|Notifications| SMTP STT -->|Generate xlsx| FOSC
SE concept — system boundary: Everything inside the box is in scope. TEMPO and the Excel package are external interfaces; we import/export but do not own them.

Design decision: DailySummary is a derived snapshot recalculated by time_calc.update_daily_summary after punches, leave sync, phone, or offsite changes. That keeps compliance and export deterministic.

6. System requirements

Requirements use “shall” language. IDs enable traceability. SHALL = mandatory · NFR = non-functional.

6.1 Functional requirements

IDRequirementPriority
FR-AUTH-01 The system shall authenticate employees using a personal PIN and signed session cookie (max age configurable; default 8 hours). shall
FR-AUTH-02 The system shall force PIN reset when pin_needs_reset is true (first login / admin reset). shall
FR-CI-01 The system shall record check-in with declared time, submission time, and location type (office / remote / offsite). shall
FR-CI-02 The system shall reject check-in when the employee is already in the checked_in state for that work date. shall
FR-CO-01 The system shall reject check-out unless the employee is in the checked_in state and declared check-out ≥ check-in. shall
FR-OFF-01 The system shall accept offsite intervals that do not overlap existing clock or offsite intervals for the same day. shall
FR-PH-01 The system shall allow phone-support hours that are additive to FOSC Normal Time. shall
FR-CALC-01 FOSC Normal Time shall equal clock + offsite + phone + BEOD credit (when earned). shall
FR-CALC-02 Target hours shall be 9h Mon–Thu, 4h Fri, 0h weekend (configurable schedule map). shall
FR-BEOD-01 BEOD credit (+1h) shall apply only if claimed/approved and raw work hours before credit ≥ configured minimum (default 6.0h). shall
FR-OFFS-01 When |declared − submission| exceeds the comment threshold, the entry shall require manager offset approval. shall
FR-LEAVE-01 Employees shall request leave (vacation, sick, COVID sick, UAE holiday) spanning one or more days. shall
FR-LEAVE-02 Pending leave shall reserve balance days; approved full-day leave shall credit target hours for each workday. shall
FR-APPR-01 Managers/supervisors shall approve or reject leave, BEOD (when not blanket), and time offsets. shall
FR-TEMPO-01 Authorized users shall import TEMPO weekly hours per employee (form or CSV). shall
FR-FOSC-01 The system shall export weekly and quarterly Excel packages with Time Keeping sheets matching FOSC attendance structure. shall
FR-DISC-01 Discrepancy Tracker shall show only shortfalls where base hours < TEMPO (hours-to-reduce), using INDEX/MATCH into week sheets col M. shall
FR-AUDIT-01 Security-relevant actions shall be written to an immutable audit log (actor, entity, old/new values, timestamp). shall
FR-PAST-01 Past-day entry shall be limited to prior workdays within the configured lookback window (default 14 days). shall

6.2 Non-functional requirements

IDRequirementType
NFR-SEC-01 PINs shall be stored only as one-way hashes; session tokens shall be signed. security
NFR-USA-01 Primary punch flows shall be completable in ≤ 3 user interactions from login list (quick check-in/out). usability
NFR-REL-01 Business rules for punch legality shall live in one service module to prevent divergent UI logic. reliability
NFR-MAINT-01 Export, leave, and time-calc logic shall be unit-testable without the browser (pure services + DB session). maintainability
NFR-PORT-01 Deployment shall support local SQLite with optional TLS and Tailscale remote access. portability

7. Acceptance criteria (selected)

Acceptance criteria make requirements testable. Format: Given / When / Then.

AC-CI-02 · FR-CI-02

Given employee E is checked in today
When E submits another check-in for today
Then the system rejects with a message that check-out is required first, and no new TimeEntry is stored.

AC-BEOD-01 · FR-BEOD-01

Given BEOD is claimed and approved, and clock+offsite+phone = 5.5h
When daily summary is recalculated
Then beod_hours = 0 and total_hours = 5.5 (minimum not met).
Given the same flags and hours = 6.0
Then beod_hours = 1.0 and total_hours = 7.0.

AC-LEAVE-02 · FR-LEAVE-02

Given a Friday with target 4h and approved full-day vacation
When leave is synced to DailySummary
Then leave_hours = 4.0, leave_approved = true, and compliance uses leave toward the daily target.

AC-DISC-01 · FR-DISC-01

Given week SDC total = 40 and TEMPO = 38
When Hours to Reduce is evaluated
Then result = 0 (base above TEMPO is not reported).
Given SDC = 36 and TEMPO = 40
Then result = −4 (shortfall only).

AC-OFFS-01 · FR-OFFS-01

Given comment threshold = 15 minutes
When declared time is 20 minutes earlier than submission
Then offset_approved is false until a manager approves the entry.

Break at End of Day: optional +1 hour paid lunch credit when policy conditions hold.

14. Verification & validation (V&V)

Verification — “Did we build it right?”

  • Unit tests on pure services (time_state, time_calc, leave_balance)
  • Integration: route + DB session for check-in / leave approve
  • Excel smoke: open generated package, evaluate formulas
  • Trace matrix: each FR has at least one test or demo script

Validation — “Did we build the right thing?”

  • Stakeholder walkthrough of weekly FOSC sheet vs contract template
  • Manager dry-run: leave + offset + export for one quarter
  • Employee usability: quick check-in from login under 10 seconds
  • Discrepancy Tracker matches “base < TEMPO only” policy
SE vocabulary: Verification checks against requirements/design. Validation checks against operational need and stakeholder acceptance. Both are required for a credible baseline.

15. Exercises for new engineers

  1. Write a new FR for “manager comments required on rejected leave.” Add acceptance criteria and point to where you would implement it.
  2. Extend the state chart: what happens if leave is approved for a day the employee already punched? Propose a rule and update FR-LEAVE.
  3. Interface change impact: if the contract moves TEMPO variance from column M to column N, list every artifact that must change (export code, discrepancy formulas, ICD, AC-DISC-01).
  4. Hazard analysis (lightweight): identify three ways incorrect hours could reach the quarterly package and a mitigation for each (process or design).
  5. Demo V&V: execute AC-BEOD-01 and AC-DISC-01 on a local instance; record evidence (screenshots + export file).
